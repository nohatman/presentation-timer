## 0. Recap of what is proven

3-byte UDP frame, subnet-directed broadcast to `:36700`:

```
byte1 = minutes,  nibble-swapped BCD   (low nibble = tens/left digit, high nibble = ones/right digit)
byte2 = seconds,  same
byte3 = state:  0x01 green  0x02 red  0x03 amber  0x04 off
```

Verified: `12:34 green` = `21 43 01`; `89:59 green` = `98 95 01`;
`12:34 off` = `21 43 04`. Pause/Resume/nudge/threshold-colour all work.
Unknown: everything with a sign, an hour, or a value the 4 BCD digits can't
hold, and any `byte3` value outside `01`–`04`.

## 2. Instruments needed (proposed — approve to add; all additive, none touch `lib/` or the bridge runtime)

### 2a. `tools/send-frame.js --raw "<b1> <b2> <b3>"`

Send one arbitrary 3-byte frame (hex). ~10 lines added to the existing tool:

```js
// after flags are parsed, before the MM:SS path:
if (flags.raw) {
  const bytes = String(flags.raw).trim().split(/[\s,]+/).map((h) => parseInt(h, 16));
  if (bytes.length !== 3 || bytes.some((b) => !(b >= 0 && b <= 255))) {
    throw new Error('--raw needs three hex bytes, e.g. --raw "10 32 05"');
  }
  var buf = Buffer.from(bytes);            // reuse the existing sender/describeFrame path
}
// ... then: const buf = flags.raw ? buf : encodeFrame({ minutes, seconds, colour });
```

Usage: `node tools/send-frame.js --raw "10 32 05" --interface Ethernet`
(supports the existing `--count` / `--interval` for 1 Hz sequences).

### 2b. `tools/sniff.js` — passive UDP listener on `:36700`

Read-only. Logs every frame with a timestamp, hex, our decode, and a `CHANGED`
marker when bytes differ from the previous frame. Prints a distinct-frame
summary on exit. Full source:

```js
'use strict';
// Passive CDEther frame sniffer. node tools/sniff.js [--diff]
const dgram = require('node:dgram');
const { describeFrame } = require('../lib/cdether');
const diffOnly = process.argv.includes('--diff');
const seen = new Map();
let prev = null;
const s = dgram.createSocket({ type: 'udp4', reuseAddr: true });
s.on('message', (m, r) => {
  const hex = [...m].map((b) => b.toString(16).padStart(2, '0')).join(' ');
  const changed = prev && prev !== hex;
  seen.set(hex, (seen.get(hex) || 0) + 1);
  if (!diffOnly || changed || !prev) {
    const marks = changed
      ? ' CHANGED:' + [0, 1, 2].filter((i) => prev.split(' ')[i] !== hex.split(' ')[i]).map((i) => 'b' + (i + 1)).join(',')
      : '';
    const dec = m.length === 3 ? '  ' + safeDecode(m) : '';
    console.log(`${new Date().toISOString()}  ${r.address.padEnd(15)}  [${hex}]${dec}${marks}`);
  }
  prev = hex;
});
function safeDecode(m) { try { return describeFrame(m); } catch { return '(non-standard)'; } }
process.on('SIGINT', () => {
  console.log('\n--- distinct frames seen ---');
  [...seen.entries()].sort((a, b) => b[1] - a[1]).forEach(([h, n]) => console.log(`  ${n.toString().padStart(5)}  [${h}]`));
  s.close(() => process.exit(0));
});
s.bind(36700, () => { s.setBroadcast(true); console.log('sniffing udp/36700 — Ctrl+C for summary'); });
```

### 3.1 Priority 1 — Negative / overtime

**Hypotheses**
- **H1 — dedicated `byte3` state:** a value `≥ 0x05` means "overtime/minus";
  the two digit bytes carry the absolute value.
- **H2 — sign bit in `byte3`:** `byte3` low bits = colour, a high bit = minus
  (so `0x05/0x06/0x07` = minus + green/red/amber, or `0x81` = minus + green).
- **H3 — minus glyph in a digit nibble:** BCD nibbles `0xA`–`0xF` render as
  special glyphs (`-`, blank). Overtime shows as `-M:SS` with the sign in the
  left position.
- **H4 — no overtime support:** the display cannot show negative; the reference
  software also clamps/flashes at zero → our current `00:00` red is correct.

**Route B — direct packet sweep (guaranteed available; ~15 min)**

Reference frame throughout: `01:23 green` = `10 32 01` (asymmetric, so a digit
shift is obvious).

1. **Baseline** — `--raw "10 32 01"` → confirm `01:23` green.
2. **`byte3` state sweep** — send, pausing to observe each:
   `10 32 05`, `10 32 06`, `10 32 07`, `10 32 08`, `10 32 09`, `10 32 0a`,
   `10 32 0b`, `10 32 0c`, `10 32 0d`, `10 32 0e`, `10 32 0f`,
   then bit candidates: `10 32 10`, `10 32 20`, `10 32 40`, `10 32 80`,
   `10 32 81`, `10 32 82`, `10 32 83`.
   Watch for: a minus sign, a blink, a colour change, a blanked digit, no
   effect (treated as an unknown state → likely `00:00` or hold).
3. **Digit-nibble glyph probe** — left position (`byte1` low nibble):
   `1a 32 01`, `1b 32 01`, `1c 32 01`, `1d 32 01`, `1e 32 01`, `1f 32 01`.
   Note which (if any) shows `-`, and which shows blank.
   Then the other three positions: `a0 32 01`…`f0 32 01` (position 2);
   `10 3a 01`…`10 3f 01` (position 4); `10 a2 01`…`10 f2 01` (position 3).
4. **Reconstruct** — if a minus glyph `0xN` was found in position 1:
   `-1:23` should be `--raw "1N 32 01"` (already sent in step 3 — confirm it
   reads `-1:23`). Try `-9:59` = `9N 95 01`, `-0:01` = `0N 10 01`.
5. **Count** — `node tools/send-frame.js --raw "<-0:01 frame>" --count 5 --interval 1000`,
   then `-0:02`, `-0:03` … by hand (or `sweep.js`): confirm it *counts*, not
   just displays one value.
6. **Colour independence in overtime** — repeat the proven overtime frame with
   `byte3` = `01/02/03` (or whatever step 2 showed) — is colour still settable,
   or forced?
7. **Edge** — the most-negative representable frame (`-9:59`, or `-99:59` if a
   two-digit-minute overtime form exists): does it wrap, clamp, or blank at the
   limit?

**Route A — reference capture (faster, if §1 confirmed a UDP output)**

1. `node tools/sniff.js` on the CDEther LAN.
2. Point Irisdown / KUMA at the CDEther (its Interspace-network / CDEther
   output; same broadcast `:36700` or unicast to the CDEther's IP).
3. Run a short timer (e.g. `00:05`) and **let it run past zero into overtime**.
4. In the sniff log, find the frame at the `00:00 → -00:01` transition and read
   which byte(s)/bits changed and how the digit bytes are populated.
5. Confirm with 2–3 direct `--raw` frames from Route B.

**"Proven" =** a specific frame renders a specific `-M:SS`; a 1 Hz sequence
counts down through zero into overtime correctly; colour behaviour in overtime
is documented; the negative limit behaviour is documented. Only then propose a

### 3.2 Priority 2 — Time of day

> **PHYSICALLY PROVEN END-TO-END 2026-09-11.** H1 confirmed: plain
> four-digit `HH:MM` frames render correctly with no protocol extension
> (results in §7). Leading-zero suppression on single-digit hours (e.g.
> `09:05` shown as `9:05`) is native physical-display behaviour, accepted
> as-is. Colon behaviour (H2 in the original hypotheses below) was **not**
> separately probed — no colon-related `byte3` value is used or needed;
> implementation only ever sends the already-proven `0x01` green state.
> Implemented in `lib/state.js`'s `deriveFrame()` - clock mode outputs
> `HH:MM` (24-hour, server-corrected, green) instead of `OFF`. **End-to-end
> rig pass completed 2026-09-11** (PT clock mode → bridge → CDEther →
> Hive): correct 24-hour `HH:MM` in green; switching Timer → Time of Day and
> Time of Day → Timer both restore the correct output immediately in either
> direction, with **no bridge restart required**; overlay message still
> overrides clock mode → OFF and clearing it restores the clock; Ctrl+C
> still sends one OFF frame and exits cleanly; countdown/pause/resume/nudge/
> amber/red are all unchanged.

**Runs now with the shipped `send-frame.js` — no new tool.**

**Hypotheses**
- **H1 — no protocol change needed:** the frame already carries 4 digits;
  sending the current `HH:MM` every second/minute with a normal colour just
  works. Clock mode on the Hive = "bridge sends `HH:MM`".
- **H2 — a distinct `byte3` state** enables a time interpretation and/or a
  blinking colon.
- **H3 — no HH:MM capability** → OFF stays correct.

**Experiment T (~5 min)**

1. `node tools/send-frame.js 12:00 green --interface Ethernet` → reads `12:00`?
2. `23:59 green`, `00:00 green`, `09:05 green` → all render as the expected
   4-digit values (no leading-zero or shift oddities)?
3. **Colon** — with the same digits, is the colon lit? steady or blinking? Send
   `--raw "21 00 01"` then `21 00 02`, `21 00 03`, and (from step 3.1's sweep)
   any `byte3` value that produced a colon/blink change. Note whether the colon
   can be made to blink (typical "time of day" affordance).
4. If Irisdown / KUMA has a **time-of-day display mode** targeting Interspace:
   `sniff.js` while it runs, compare to a plain countdown frame — does it set a
   distinct state byte or a colon-blink flag?

**"Proven" =** representative `HH:MM` values render correctly and the colon
behaviour is documented. If H1 holds (likely), P2's "clock mode → send `HH:MM`"
needs **no** protocol extension — just a bridge-side mode.

### 3.3 Priority 3 — `> 99:59` (low priority, ~3 min)

1. `--raw "99 95 01"` → confirm `99:59` (already verified).
2. `--raw "99 95 05"` … `"99 95 0f"` — does any state reinterpret the digits as
   `HH:MM` (i.e. `99:59` → "99 hours 59 min" semantics, or a rollover)?
3. `--raw "a0 00 01"`, `--raw "f0 00 01"` — does a non-BCD `byte1` unlock
   anything (hundreds, hours)?
4. If nothing: **99:59 is the hard physical limit for `MM:SS` mode** — record
   that; long durations are then a P2 "show `HH:MM` instead" decision, not a
   protocol gap.

## 4. Route recommendation

| Investigation | Best route | Rationale |
|---|---|---|
| **Negative / overtime** | **Reference capture first** (Irisdown or KUMA → CDEther UDP, sniff `:36700`) **if** a UDP output exists (§1); **direct packet sweep** otherwise, and always as confirmation + edge-mapping | The encoding could be a state byte, a sign bit, or a glyph nibble — a 2-minute capture of a known-good implementation resolves which, versus a blind sweep. Direct packets then confirm and map the limits. |
| **Time of day** | **Direct packet, now** (`send-frame.js HH:MM`) — almost certainly already works; reference capture only to clarify colon/blink | Our frame already encodes any 4 digits; the real question is product behaviour + colon, answered by sending `23:59` and looking. |
| **`> 99:59`** | **Direct packet** (a few frames); otherwise fold into the P2 clock/long-form decision | Cheap to check; almost certainly a hard BCD limit. |

**Irisdown vs KUMA:** use whichever you have that can output to the CDEther over
the **network** (UDP `:36700` or unicast to the CDEther). If a tool only drives
Interspace displays over **serial/USB**, sniffing UDP won't see its frames and a
serial-line analyser is out of scope for "quick interactive" — fall back to
direct packet experiments (which are guaranteed to work with the exact rig
already proven). If both tools have a network output, **Irisdown Countdown /
Stage Timer** has the more established overtime semantics.
